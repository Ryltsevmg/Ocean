# Запустите DSH за сетевым прокси

DSH направляет свои исходящие запросы — вызовы моделей, веб-поиск, поиск страниц и серверы MCP по HTTP — через прокси-сервер, названный стандартными переменными среды прокси. Он читает их при запуске; больше ничего не нужно настраивать. Несколько маршрутов остаются прямыми по дизайну или по лимиту времени выполнения, указанному в разделе «Что остается прямым» ниже.

<a id="export-the-variables"></a>

## Экспорт переменных

```sh
export HTTPS_PROXY=http://127.0.0.1:7890
export HTTP_PROXY=http://127.0.0.1:7890
```

Поместите обе строки в свой профиль оболочки, чтобы каждое обращение `dsh` наследовало их, или в `$DSH_HOME/.env` (`~/.dsh/.env` по умолчанию) рядом с вашим ключом API; экспортируемая переменная всегда выигрывает над этим файлом. Собственный `.env` не может установить их: он поставляется с `git clone`, и DSH отказывается запускать, а не позволять репозиторию решать, куда идет ваш трафик.

Прокси-сервер, который нуждается в учетных данных, берет их в URL: `http://user:password@proxy.example:8080`. DSH никогда не печатает URL обратно: диагностические имена переменной, которую он отклонил, поэтому ни имя пользователя, ни пароль нигде не отображаются.

<a id="why-your-browser-is-proxied-but-your-terminal-is-not"></a>

## Почему ваш браузер находится рядом, а ваш терминал нет

Это самый распространенный сюрприз, и он не специфичен для DSH. Не существует единого «системного прокси», которому подчиняется все программное обеспечение — есть три несвязанных механизма:

| Механизм | , который следует за ним |
|---|---|
| Настройки прокси-сервера операционной системы | Safari, большинство нативных приложений для macOS, Chrome и Edge |
| The `HTTP_PROXY` / `HTTPS_PROXY` переменные окружающей среды | `curl`, `git`, `npm`, `pip`и DSH |
| Режим TUN (виртуальный сетевой интерфейс) | Все, прозрачно |

Переключатель «системный прокси» в прокси-приложении, таком как Clash, записывает только первый. Браузеры подбирают его; инструменты командной строки никогда не видят его. Вот почему экспорт переменных является отдельным шагом, и почему включение режима TUN заставляет работать оба без каких-либо переменных вообще.

DSH не считывает настройки прокси операционной системы. Экспортировать переменные или использовать режим TUN.

<a id="choose-what-stays-direct"></a>

## Выберите то, что остается прямым

`NO_PROXY` Список хостов для прямого доступа:

```sh
export NO_PROXY=internal.example.com,.corp.example.com,registry.local
```

Вход называет хост и сопоставляет его с каждым поддоменом под ним: `NO_PROXY=example.com` также отправляет `api.example.com` напрямую. Ведущий `.` или `*.` принимается и означает одно и то же. Вход может нести `:port`, а `*` обходит все.

**Диапазоны CIDR не работают.** Список обхода операционной системы часто содержит записи, такие как `10.0.0.0/8` или `192.168.0.0/16`; копирование их в `NO_PROXY` не имеет эффекта. Используйте имена хостов или суффиксы домена.

Вам не нужно перечислять `localhost` или `127.0.0.1`. DSH всегда обходится без обратной связи, потому что его собственный веб-интерфейс и локальные серверы в противном случае будут маршрутизироваться через прокси-сервер и цикл.

<a id="limits-worth-knowing"></a>

## Ограничения, которые стоит знать

**Прокси SOCKS не поддерживаются. Значение** A `socks5://` сообщается при запуске и пропущено, и DSH подключается непосредственно к схеме, которая назвала его — установка `HTTPS_PROXY=socks5://…` вместе с пригодным для использования `HTTP_PROXY` оставляет `https:` прямым, а не заимствует HTTP-прокси. Направьте переменные на HTTP-порт вашего прокси-приложения — большинство из них отображают оба, а HTTP-один обычно является соседним номером порта.

**`ALL_PROXY` Одного достаточно.** DSH возвращается к нему для обеих схем, хотя Узел и завиток различаются по этому. `HTTPS_PROXY` Явно все еще яснее.

**Корпоративному прокси-серверу, перехватывающему TLS, нужен сертификат.** Если запросы терпят неудачу с ошибкой сертификата, как только прокси-сервер будет доступен, узел точки в пакете CA вашей организации перед запуском:

```sh
export NODE_EXTRA_CA_CERTS=/path/to/corporate-ca.pem
```

Узел читает эту переменную только при запуске процесса, поэтому экспортируйте ее перед запуском. `dsh`.

**Инструменты DSH запускаются для вас с помощью того же прокси. Команды** в инструменте bash, `git`, `gh`и MCP-серверах, запущенные в процессе работы с детьми, наследуют эти переменные. Программа «Детский узел» использует собственное установленное время выполнения: Узел 22.21+ и Узел 24+ соблюдают эти переменные; более старое время выполнения подключается напрямую. Если одна из ваших переменных прокси содержит значение DSH, отклоненное, например, URL-адрес SOCKS, инструменты на основе узлов также подключаются напрямую, а не не запускаются, в то время как `curl` и `git` по-прежнему читают это значение.

**Пароль в URL-адресе прокси-сервера также достигает этих инструментов.** `HTTPS_PROXY=http://alice:s3cret@proxy.example:8080` — это нормальная переменная среды, поэтому каждая команда, которую запускает DSH, включая те, которые пишет модель, может прочитать ее, а команда, которая печатает ее среду, вводит пароль на выходе, который сохраняется. Вот как переменная уже ведет себя для всего остального в вашей оболочке. Если это имеет значение, дайте прокси-серверу точку входа без учетных данных или проверьте ее каким-либо другим способом, чем в URL-адресе.

<a id="what-stays-direct"></a>

## Что остается прямым

Не каждый запрос DSH проходит через прокси-сервер:

- **Что-нибудь на этой машине.** Лопбэк всегда прям: `localhost`, в целом `127.0.0.0/8` диапазон, `::1`и `0.0.0.0`Прокси-сервер не может с пользой добраться до службы, которая слушает только локально.
- **Код пишет модель. Работники** Workflow и процессы Node ptc-runtime не получают настроек прокси-сервера, поэтому сценарии, созданные моделью, не могут читать URL-адрес прокси-сервера, который может содержать пароль. Прямые запросы должны сами настраивать любой требуемый прокси-сервер и оставаться предметом выполнения песочницы.
- **Использование телеметрии.** Экспортер OTLP использует собственный HTTP-клиент Node, а не тот, который настраивает прокси, поэтому телеметрия подключается напрямую и просто выходит из строя там, где блокируется прямой выход. От этого ничего не зависит в DSH. `DSH_TELEMETRY_MODE=DISABLED` Чтобы полностью его выключить.
- **`web_fetch` По буквальному частному адресу.** URL-адрес, именующий адрес как `http://10.0.0.5/` Отказывается, а не передается прокси, тот же отказ он получает без прокси настроен.

<a id="check-that-it-worked"></a>

## Проверьте, что это сработало

Попросите агента принести страницу и посмотреть журнал подключения вашего прокси-приложения:

```sh
dsh --profile headless "fetch https://example.com and tell me the page title"
```

Если запрос не появляется, подтвердите, что переменные выживают в среде DSH:

```sh
env | grep -i proxy
```
