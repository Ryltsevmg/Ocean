# Ocean Linux 发布准备

[English](README.md) | 中文

参考文档：离线验证及剩余安装要求。此目录不会启用自动更新或发布版本。

## 当前实现

`../scripts/ocean-release-manifest.mjs` 准备确切的未签名 JSON 字节，并使用调用方独立提供的公钥验证分离式 Ed25519 签名。公钥必须来自经过批准且固定的信任存储，绝不能来自 manifest（元数据清单）或其下载端点。SHA-256 和大小将归档与已签名元数据绑定。返回经过认证的元数据之前，会检查产品、架构、渠道、有效期，以及调用方提供的单调序列号下限。有效期最长为七天。最终产物路径必须是普通文件，不能是符号链接。验证完全离线，不会解压、安装、切换启动器、修改配置档案或重启进程。

验证器单独接受产物路径，因为下载缓存可能使用临时文件名。其结果仅表示某一时刻的完整性检查，不是安装授权，也不保证文件随后不会被替换。安装器必须保护暂存目录，并重新验证实际使用的字节。仅有校验和文件不能证明发布者身份。测试仅将公开的 RFC 8032 密钥用作 fixture（测试前置数据）；已发布客户端绝不能信任该密钥。

手动 GitHub 打包工作流以原生 `ubuntu-24.04` x64 或 `ubuntu-24.04-arm` ARM64 运行器为目标，检查原生架构，并保留无签名归档、校验和以及源码／运行元数据供评审。两种架构分别需要成功触发并完成运行。托管 ARM64 访问权限、原生包内容和打包后 UI 的运行仍属于待验证要求。构建证据仅供参考，并非已签名的证明。没有任何工作流会创建签名密钥或将产物发布为版本。

在仓库根目录运行 `node --test apps/desktop/scripts/ocean-release-signing.test.mjs apps/desktop/scripts/ocean-release-manifest.test.mjs apps/desktop/scripts/ocean-linux-update-policy.test.mjs apps/desktop/scripts/ocean-linux-archive-policy.test.mjs` 执行离线测试。现有 Electron 更新／任务收尾测试仍需独立执行；此测试不覆盖安装。

## 操作者离线签名

`../scripts/ocean-release-signing.mjs` 固定了新的 Ocean Electron Ed25519 发布者密钥 `ocean-electron-release-v1`。其 SPKI SHA-256 指纹为 `91f3e2aeb0880fa5ec0550ad5a76d99bec1496a92ff4b440fd449eaf39d7289f`。仓库仅提交公钥，不复用旧项目的发布密钥。`verifyOceanRelease` 使用此固定密钥，而非由输入提供的发布者公钥；它是离线辅助函数，尚未集成到已安装的更新器中。

操作者将私有 PKCS8 PEM 保存在仓库外的本地私有目录（0700）中，文件权限为 0600。仅有本地存储并不构成独立备份：公开发布前，须确认 Bitwarden 中有可独立恢复的副本。不得将私钥放入参数、日志、产物或通用 CI 凭据中。签名命令接受的是**路径**，绝不是私钥本身。它拒绝符号链接、硬链接、过宽权限、不匹配的密钥及已存在的输出。写入公开发布元数据之前，它会验证签名和产物。I/O 错误后留下的部分输出不是可发布版本，不得发布。

审查源码修订和构建归档后，选择尚未使用且单调递增的序列号，以及相隔不超过七天的 ISO 时间戳。示例（替换所有占位符；此命令不会发布）：

```sh
node apps/desktop/scripts/ocean-release-signing.mjs \
  --artifact /absolute/path/ocean-linux-x64.tar.gz \
  --private-key /private/operator/path/ocean-release.private.pem \
  --output /absolute/path/new-signed-metadata \
  --version 0.2.2-rc.3 --sequence 1 --channel nightly --target linux-x64 \
  --created-at <ISO-UTC-created-time> --expires-at <ISO-UTC-expiry-time>
```

输出为 `manifest.json` 和原始 64 字节的 `manifest.sig`；两者均不含秘密。该命令不更新持久序列号账本，也不上传、启用或发布。操作者必须防止序列号复用，并在发布前立即重新验证产物的确切字节；签名器不会冻结输入归档。这是 Linux manifest 签名，不是 macOS 公证或 Windows Authenticode。

## 事务策略

`../scripts/ocean-linux-update-policy.mjs` 实现 staged → quiescing → ready → activating → checking → complete 的纯决策逻辑，条件不满足时拒绝继续。调用方必须先持久化返回的记录，再执行返回的操作。每个事件（包括失败）都必须同时匹配事务身份和当前修订。安装批准还绑定源版本、目标版本及归档摘要。事务 ID 必须唯一，日志适配器不得复用；所有必需的观察事实都必须显式提供。缺少批准、验证过期、任务状态未知或任务仍活跃、收尾未完成、缺少关闭确认，或一致性备份未经验证，都会阻止启用。任务收尾后，启用前必须根据当前信任存储、有效期和持久序列号下限重新完整验证 manifest；不得复用最初批准时的验证。暂存摘要改变或未保留旧安装同样会阻止切换。只有目标版本正确且运行时就绪，事务才可完成。

崩溃后，每个未完成事务都必须接受检查；策略绝不自动重放切换、重启进程、降级二进制或恢复数据。失败使事务进入恢复状态。独立的二进制回滚判定要求重新批准、任务静止、已验证的旧二进制，以及明确的配置档案兼容性；仅有备份并不足够。测试覆盖阶段中断、过期事件、事实缺失、活跃工作及已迁移配置档案。

此策略不产生文件系统或进程副作用，也不是安装器。持久化、事务独占归属、实际解压、产物验证、任务观察、启动器修改、健康检查及恢复 UI 必须由可信的主进程适配器实现。渲染进程不得提供 `taskStateKnown` 或 `profileCompatibleWithPrevious` 等事实；这些事实必须来自经过验证的本地状态。策略中的布尔证据不能替代实际检查。接入回滚判定前，适配器必须将批准和观察结果绑定到确切事务、保留的二进制摘要以及源／目标版本。普通候选版本选择必须拒绝版本降级，即使其发布序列号更高；降级恢复属于独立操作。未来的日志适配器必须拒绝未知 schema，并采用原子持久写入；启用过程中崩溃时必须同时检查日志和启动器，因为任一副作用都可能已完成。

## 归档布局策略

`../scripts/ocean-linux-archive-policy.mjs` 验证解析器解析出的应用根目录元数据，不产生文件系统副作用。它拒绝绝对路径、路径穿越和非规范路径、重复条目、非目录祖先、硬链接、特殊文件、格式错误的 Unicode 路径，以及过多的条目（包括推导出的父目录）或过大的解压后字节数。仅允许随包 Python 的 `bin/python` 和 `bin/python3` 别名，两者都必须相对指向归档内同一个非空的普通 `python3.X` 解释器文件。这保留了现有 primary-runtime smoke 要求；其他链接均被拒绝。创建这两个别名前必须先落盘普通文件和目录，绝不能沿归档提供的链接写入。

这不是 tar 解析器或解压器。未来的适配器必须拒绝不支持的头部，在验证有效 PAX/GNU 路径之前不得先清理路径穿越，并显式识别归档顶层包装目录。使用新的私有暂存目录，绝不使用现有安装或配置档案；拒绝已存在的路径组件，并对实际流式读取字节数执行限制。不得恢复归档中的所有权、setuid/setgid 位或不可信元数据。写入前验证完整计划，创建目录／文件时不跟随链接，验证解释器内容／权限及运行时布局，最后仅创建计划中的别名。同用户竞争、暂存归属、使用不可变且已验证的归档、中断清理及原子启用仍由适配器负责。

## 此处尚未实现的安装要求

Linux 包目前是 tar 归档，并被有意排除在继承的发布器之外。继承的 `electron-updater` 集成不会将这些归档变成安装器。不得在客户端中嵌入 GitHub 个人访问令牌来获取私有版本。分发需要经过批准的 HTTPS 端点或单独设计的认证下载服务，以及独立批准的签名身份和密钥保管方案。仅设置现有的 `OCEAN_DOWNLOAD_ORIGIN` 不足以实现 Linux 安装。

未来的安装器必须在已安装应用旁暂存版本化目录，再次验证已签名 manifest 和归档，拒绝不安全的归档路径、硬链接、特殊文件及不支持的符号链接，限制解压后大小，验证预期的可执行文件／运行时布局，并保持运行中的安装不变。安装必须明确获得授权。复用现有的主进程任务授权、准入锁、收尾及正常关闭流程；状态未知、未经批准的活跃工作、收尾失败或关闭失败都必须终止安装。普通退出时不得自动安装。

仅在暂存已验证且任务静止后切换。将每个持久步骤写入日志，原子替换启动器目标，并保留旧版本。仅成功启动还不够：将事务标为完成之前，必须验证本地运行时就绪状态及最终版本。中断操作需要幂等恢复。旧版本仍在执行或所有者尚无可恢复的后备版本时，绝不能删除它。

二进制回滚与数据回滚不同。Ocean 会话代次和 SQLite schema 版本单调递增；没有明确的兼容性证据，旧二进制不得打开已被新二进制迁移的配置档案。在可能迁移数据的升级之前，应先停止写入，再创建一致且经过验证的备份，包括处理 SQLite WAL。回滚不得静默丢弃升级后产生的工作。备份可能包含凭据和私人对话；须保存在本地并保护权限，不得随诊断信息或发布产物上传。

序列号下限必须由安装器独立持久保存；manifest 提供的下限无法防止重放。降级需要单独且明确的恢复操作及兼容性检查，而不是降低普通序列号下限。生产启用前，密钥轮换需要独立可信的过渡和撤销设计。

## 发布检查清单

- 将当前功能提交与远程 main 协调，保留 Ocean Codex、品牌、导航及反馈修改；运行针对性测试和最终构建／类型检查。
- 验证两种托管架构，并独立验证打包运行时、原生依赖、权限、启动、托盘、任务保护及离线插件路径。
- 选择版本、渠道、分发 URL、签名身份及密钥保管方案。秘密不得进入仓库文件、日志、客户端 bundle 或不可信 CI 任务。
- 完成并测试 Linux 暂存／安装／恢复实现，包括每个日志步骤上的中断、并发更新、磁盘空间不足、篡改、重放、错误架构、活跃任务、未知任务状态及数据迁移兼容性。
- 在隔离配置档案上测试从实际安装的旧 Ocean 构建进行签名更新。这也用于确定现有无签名安装的引导路径；仅发布元数据不能使它们获得可信更新器。
- 仅在获批且验证完成后发布。保留发布说明、不可变源码 SHA、产物摘要、分离式签名及回滚说明。已发布的候选版本并不自动成为稳定版本。
