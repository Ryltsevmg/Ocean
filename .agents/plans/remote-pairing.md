# Подключение Desktop к Host по ссылке спаривания

Статус: проект (draft), 2026-11-24. Продолжает [remote-connection.md](remote-connection.md): там описан обмен токена устройства на сессию, здесь — как получить токен без ручного ввода и как не привязывать совместимость к коммиту. Ориентир — [Remote access](https://raw.githubusercontent.com/pingdotgg/t3code/main/docs/user/remote-access.md) и [Environment authentication](https://raw.githubusercontent.com/pingdotgg/t3code/main/docs/internals/04_environment-auth.md) у T3 Code; их модель устройств не совпадает с нашей, переносим только перечисленные ниже решения.

## Цель

Пользователь выполняет на сервере одну команду, получает ссылку, открывает её на своём устройстве и подключается без копирования адреса и токена. Desktop и Host разных сборок одной версии работают вместе. Для Tailscale не нужны ручной сертификат и отдельный порт.

## Шаг 1. Ссылка спаривания

Принцип: ссылка одноразова и короткоживуща; она обменивается на обычный токен устройства, поэтому `rotate`, `revoke`, лимиты сессий и cookie-вход не меняются.

1. Host. В реестре устройств добавляется список ожидающих грантов: `{ id, hash, label, expiresAt }`. Секрет гранта — 32 случайных байта в base64url, хранится только хеш, срок жизни по умолчанию 10 минут, настраивается полем конфигурации плагина.
2. Admin-команда `pair { label, ttlSeconds? }` возвращает `{ grantId, secret, expiresAt }` один раз. CLI печатает ссылку `ocean://pair?host=<https-адрес>&label=<метка>#<секрет>`. Секрет во фрагменте, как у T3 Code: он не попадает в журналы прокси и реферер.
3. Host. Новый маршрут `POST /connect/pair` с заголовком `Authorization: Bearer <секрет гранта>` и протокольной версией. В одной записи реестра он сверяет хеш и срок, удаляет грант и выпускает устройство (`issue(label)`); ответ `200 { id, token }` с `cache-control: no-store`. Повторное использование, просроченный и неизвестный грант дают одинаковый `401`. Частота попыток ограничивается тем же окном, что и обмен токена.
4. Клиент. `DeviceClient.pair(secret, label, signal)` возвращает токен; дальше вход идёт прежним `login`. Проверка идентичности Host до отправки секрета: `HEAD /connect` с версией протокола, как при сохранённом подключении.
5. Desktop. Обработчик `ocean://pair`: окно подключения открывается с подставленными адресом и меткой, показывает адрес для подтверждения; секрет остаётся в памяти main-процесса и не передаётся renderer. Кнопка «Подключиться» меняет токен на устройство и сохраняет его через safeStorage. Ручной ввод адреса и токена остаётся запасным путём.
6. Ссылку также можно вставить в поле адреса: renderer распознаёт `ocean://pair` и отправляет её целиком в main.

Критерии готовности: гранты одноразовы и не работают после срока; повторный вход по токену устройства не требует ссылки; тесты Host, клиента, main-процесса и формы; проверка на живом Host `bigpc`.

## Шаг 2. Совместимость по версии

Сейчас любое расхождение `commit` блокировало подключение, хотя протокол устройства (`ocean-device-protocol`) уже версионирован. Сделано:

1. Desktop требует равной `release.version` и не сравнивает `commit`. Расхождение коммита пишется в журнал main-процесса с обоими значениями.
2. При разных версиях сообщение называет обе версии (`remoteVersionMismatch`); при нечитаемом релизе остаётся общее `remoteProtocolIncompatible`.
3. Список возможностей (`capabilities`) в boot-граф не добавлен: наличие спаривания определяется самим маршрутом `/connect/pair` (404 и ответ без идентичности Host дают `DEVICE_PAIRING_UNSUPPORTED`). Отдельный список возможностей понадобится, когда появится вторая функция, которую нельзя распознать по маршруту.

Остаточный риск: проверка не сравнивает ABI клиентских модулей, поэтому две сборки одной версии из разных коммитов могут отличаться; для непубликованных изменений нужен один и тот же коммит.

Критерии готовности: сборки одной версии с разными коммитами подключаются; другая версия получает сообщение с обеими версиями; тесты на каждый исход.

## Шаг 3. Tailscale без ручного TLS

1. `ocean serve --tailscale-serve [--tailscale-serve-port N]` вызывает `tailscale serve --bg --https=<порт>` для локального порта Host, читает DNS-имя узла из `tailscale status --json` и использует его как `--public-url` и `--trusted-host`. Host слушает loopback без TLS; сертификатом занимается Tailscale.
2. Ошибки Tailscale (нет MagicDNS, нет HTTPS-сертификатов, нет прав оператора) сообщаются при запуске с названием причины; Host не запускается молча без маршрута.
3. Команда `pair` печатает ссылку с этим адресом.

Критерии готовности: на `bigpc` Host доступен по `https://bigpc.tail71ee4f.ts.net/` без ручных сертификатов и таймера обновления.

## Следующие шаги

Порядок выполнения: 5 (права устройства и список), 6 (несколько маршрутов), 4 (запуск по SSH). Шаг 4 идёт последним: он меняет модель доверия клиента.

### Шаг 5. Права устройства

Сделано (5a): каталог прав `sessions:read`, `sessions:write`, `files:read`, `files:write`, `terminal:operate`, `settings:manage`; хранение в записи устройства; `--scope` у `create` и `pair`; политика шлюза берёт объединение прав живого входа устройства. Устройство без сохранённых прав получает все, как раньше. Права только сужают: расширение — это новое устройство и отзыв старого.

Закрыто 2026-11-26 существующими пакетами, отдельной работы не потребовалось: `@ocean/ocean-api-device-controller` (namespace `devices` с `list` и `revoke`) и `@ocean/ocean-client-ui-settings-devices` (секция настроек `devices`) смонтированы в `packages/bundle/web-app/cordis.patch.yml` без условия отключения, кроме профилей `remote-device` и `connect` у контроллера. Секция регистрируется под `ctx.remoteAccess.whenAccess('devices/list')`, поэтому появляется там, где клиент владелец Host. Для чужого Host Desktop подключается устройством, а `devices/*` не входит ни в один device scope — это намеренная граница: устройство не управляет другими устройствами. Тесты: 28 в двух пакетах.

### Шаг 6. Несколько маршрутов к одной машине

Сделано: сохранённое подключение описывает машину, а не адрес. Запись хранит идентичность Host, токен и все HTTPS-маршруты, которые к ней ведут, поэтому одна машина по локальной сети и по Tailscale — это одна запись и один токен. Маршрут всегда ведёт к одной машине: сохранение под другой идентичностью переносит маршрут и удаляет машину, у которой не осталось маршрутов. Записи прошлых версий (адрес + токен на запись) читаются как машины, сгруппированные по идентичности.

Личность Host проверяется до отправки секрета: `DeviceClient.probe` делает `HEAD /connect` без учётных данных. Форма показывает, какая машина отвечает по адресу, и перечисляет её другие маршруты. При подключении без введённого токена к незнакомому адресу приложение спрашивает личность и переиспользует токен, сохранённый для этой машины. Для уже сохранённого маршрута запрос не нужен: вход и так закреплён за сохранённой идентичностью.

### Шаг 4. Запуск Host по SSH

Сервер уже поставляется с основным дистрибутивом. Проверено 2026-11-24 на `bigpc` по релизу `v1.0.0`: Linux-архив `ocean-<версия>-linux-<arch>-unsigned.tar.gz` (465 МБ, 1,4 ГБ после распаковки; контрольная сумма совпала с `SHA256SUMS`) содержит `resources/runtime/cli/bin/ocean` с собственным Node. Команда `ocean serve` запускается без исходников, pnpm и npm и отвечает на `/connect`. Это же снимает конфликт версий: приложение берёт архив той версии, которой оно само является.

#### Решение о доверии принято по факту

Проверено 2026-11-24 на живом Host `bigpc` (сборка из `feat/remote-pairing-tailscale`): на plain HTTP по loopback `HEAD /connect` и `POST /connect` с валидным токеном устройства отвечают **403**. Host сам отвергает незашифрованный device-вход, поэтому SSH-туннель с `http://127.0.0.1:<порт>/` невозможен без ослабления защитного барьера самого Host — а это изменение серверной модели безопасности, а не клиентской настройки.

Отсюда шаг 4: SSH нужен только чтобы **поставить и запустить** Host на удалённой машине, а подключение идёт по tailnet-адресу из шага 3. TLS и проверка сертификата остаются штатными, никаких новых послаблений в клиенте не появляется. Требования к удалённой машине: Linux x64 или arm64, `curl` или `wget`, `tar`, `sha256sum`, работающий Tailscale с MagicDNS и HTTPS-сертификатами.

Порядок: SSH ставит архив нужной версии в `~/.ocean-server/<версия>/`, сверяет SHA-256, запускает `ocean serve --tailscale-serve` и печатает tailnet-адрес; приложение подключается к этому адресу обычным способом. Приложение останавливает только тот Host, который запустило само.

Сделано в `apps/desktop/src/remote-ssh.ts`: шаги `inspect` (Linux, архитектура, наличие `curl`/`wget`, `tar`, `sha256sum`), `download`, `verify` (SHA-256 по опубликованному `SHA256SUMS`), `extract` (распаковка и проверка, что архив умеет `--tailscale-serve`), `serve` (приватный каталог 0700 для админ-сокета, обёртка `tailscale` с откатом на `sudo -n`, запуск через `setsid nohup`), `pair` (одноразовая ссылка через админ-сокет). Ошибки классифицированы по шагам и не содержат вывода SSH.

Проверено на `bigpc` 2026-11-24: `inspect`, `download`, `verify`, `extract` проходят на опубликованном архиве 1.0.0; `serve` и `pair` проверены на сборке этой ветки — Host печатает `https://bigpc.tail71ee4f.ts.net:8445/`, выдаёт ссылку спаривания, клиент по ней спаривается, входит и выходит, а при остановке Host сам снимает свой Tailscale-маппинг.

Проверено вживую 2026-11-26 на чистой машине `bigpc` (Linux x86_64, ни одного установленного Host): `provisionRemoteHost` прошёл `inspect → download → verify → extract → serve → pair`, Host поднялся, `/connect` ответил 204 с идентичностью. Спаривание по выданной ссылке создало устройство, токен (80 символов) принят, вход прошёл.

Живой прогон нашёл два дефекта, которых не было видно в тестах, оба исправлены:
1. На `bigpc` порт 443 занят другим сайтом `tailscale serve` (`/runneos/`), и Host отказывается его вытеснять — провижининг падал на шаге `serve` уже после скачивания 444 МБ. Теперь порт выбирается по `tailscale serve status`: 443, если свободен, иначе первый из 8443/9443/10443. Ключи `TCP` со `HTTPS: true` — это свои публикации Host, а не чужие, поэтому занятыми они не считаются.
2. Повторный запуск падал с `EADDRINUSE` на admin-сокете: Host от прошлого прогона оставался жив и по контракту не отдаёт сокет. Теперь провижининг останавливает свой прежний процесс и убирает сокет.

Релиз `1.1.0` опубликован 2026-11-26: PR #112 слит в `main`, PR #113 поднял версию, Linux-архивы `x64` и `arm64` собраны workflow и приложены к релизу вместе с `SHA256SUMS` и `build-evidence-*.json`. В архиве `1.1.0` есть `@ocean/ocean-api-port-forward-controller/lib/index.js` и `connect --pair`, то есть то, чего не было в `v1.0.1`.

Проверено вживую на `bigpc` после релиза: провижининг поставил `1.1.0`, выбрал свободный порт 8443 сам (443 и 10443 заняты) и выдал pairing-ссылку; устройство спарилось; проброс порта открыл локальный сокет на клиенте и вернул настоящий HTTP-ответ от `python3 -m http.server` на Host через реальный Gateway; список для `/ports` пришёл как `[49912]`, строка `localhost:49912`. Тестовые устройства отозваны, служба остановлена.

Побочный дефект релиза: бамп версии оставил у `plugin-market` диапазон `engines.ocean >=1.0.0 <1.1.0`, из-за чего Loader отключал плагин и все собранные снапшоты несли предупреждение в stderr. Исправлено в релизном PR до слияния.

Ограничение, которое остаётся: проброс портов и `ocean connect --pair` в `v1.0.1` отсутствуют, поэтому вживую их проверить нельзя до релиза из ветки. Сквозной путь проброса покрыт тестом против настоящего Gateway.

Ограничение снято 2026-11-26: релиз `v1.0.1` опубликован и содержит `--tailscale-serve` (коммит с `--tailscale-serve` вошёл в тег), Linux-архивы `ocean-1.0.1-linux-{x64,arm64}-unsigned.tar.gz` и `SHA256SUMS` доступны, а имена, которые запрашивает `archiveName`, совпадают с опубликованными ассетами; `app.getVersion()` равен `1.0.1`. Остаётся только проверка на живой машине. Историческое ограничение: провижининг ставит архив версии приложения, а в `v1.0.0` флага `--tailscale-serve` не было.

Принятое решение для шагов 1–3 и 5–6:

1. Целевой Host: Linux x64 и arm64 с `curl` или `wget`, `tar`, `sha256sum`. macOS и Windows как удалённые Host не рассматриваются.
2. Приложение скачивает на Host архив `v<версия приложения>` из релиза, сверяет SHA-256 с `SHA256SUMS`, распаковывает в `~/.ocean-server/<версия>/` и запускает `ocean serve` на loopback.
3. Клиент подключается через SSH-туннель к loopback. Сейчас клиент принимает только HTTPS, а Host отклоняет plain HTTP с 403, поэтому нужен явный режим туннеля: HTTP допустим только к `127.0.0.1` через туннель, который приложение открыло само. Это решение о доверии, оно требует отдельного ревью.
4. Приложение останавливает только тот Host, который запустило. Уже работающий Host при отключении остаётся.
5. Опционально позже: архив только сервера (без Electron, около 250 МБ) в тот же релиз, если размер скачивания станет проблемой.

Ограничение: релиз должен быть опубликован с архивом для нужной версии и архитектуры; у неподписанных сборок разработки архива нет.

### Шаг 7. Pairing для браузера, CLI и QR

Шаг 1 дал ссылку только Desktop: `ocean://pair` открывает одно приложение, страница входа в браузере и `ocean connect` ссылку не понимают, QR-кода нет. Переносим у T3 Code одно решение: одна ссылка и QR на устройство; ссылку открывают в браузере, вставляют в приложение или передают в CLI.

1. Ссылки. `ocean remote-device pair` печатает в JSON два поля: `link` (`ocean://pair`, как раньше) и `web` — адрес Host с грантом во фрагменте, `https://<host>/<mount>#pair=<грант>`. Фрагмент не уходит на сервер и в журналы прокси. Метка и права гранту уже присвоены на Host, поэтому в `web` их нет. Обе ссылки тратят один грант: срабатывает первая.
2. QR. Флаг `--qr` печатает в stderr QR-код ссылки `web`; stdout остаётся машинно-читаемым JSON. Кодирование — `uqr` (MIT, без зависимостей), рендер блоками Unicode в терминале.
3. Общий разбор. `parsePairingLink` переезжает из `apps/desktop/src/remote-pairing.ts` в `@ocean/ocean-client-connection/device`; рядом `parsePairingUrl` для формы `web`. Desktop и CLI пользуются одним разбором.
4. Браузер. Страница входа при загрузке находит `#pair=<грант>`, сразу убирает его из адреса через `history.replaceState`, обменивает грант (`POST ./connect/pair`), входит по токену (`POST ./connect`) и перезагружается. Токен страница не хранит: после срока cookie устройство спаривается заново или вводит токен. Поле принимает и вставленную ссылку `ocean://pair`; если её `host` не совпадает с адресом страницы, грант не отправляется.
5. CLI. `ocean connect --pair <ссылка>` вместо `--url` с `--token-env` или `--token-stdin`: обменять грант, войти, выполнить команду. Токен нового устройства печатается в stderr один раз: иначе он теряется, а устройство остаётся в реестре.

Критерии готовности: QR сканируется и открывает страницу входа, которая спаривается без ввода; `ocean connect --pair` выполняет команду и печатает токен; ссылка с чужим `host` не отправляет грант; тесты страницы, CLI и Desktop; README en/zh и upgrade guide.

Сделано 2026-11-25: `pairingUrl` и флаг `--qr` в `device-admin-client.ts`, рендер `qrTerminal` в `packages/bundle/web-app/src/pairing-qr.ts`; `parsePairing`, `parsePairingLink`, `parsePairingUrl` в `packages/client/connection/src/device-pairing.ts`; страница входа и `--pair` по пунктам 4–5. QR проверен независимым декодером (`jsQR` во временном каталоге): из терминальной строки восстанавливается исходная ссылка. Upgrade guide не нужен: изменения аддитивные, ни одна прежняя команда, ключ или формат данных не меняется. Ручная проверка сканирования телефоном на живом Host остаётся открытой.

### Шаг 8. Автопереключение маршрутов

Шаг 6 сохранил маршруты машины, но при подключении берётся введённый адрес или последний сохранённый; остальные маршруты при обрыве не пробуются.

Сделано 2026-11-25, выбор маршрута при подключении (8a): `apps/desktop/src/remote-routes.ts`. Для сохранённой машины с несколькими маршрутами `answeringRoute` идёт по порядку — введённый или последний сохранённый маршрут, затем остальные от недавних к старым — и берёт первый, который отвечает как эта машина. Каждый маршрут спрашивается безымянным `HEAD /connect` (`DeviceClient.probe`) с таймаутом 2,5 с; недоступный, молчащий или ответивший другой идентичностью маршрут пропускается. Если не ответил ни один, вход идёт по выбранному маршруту и сам сообщает причину отказа. Машина с одним маршрутом не спрашивается: лишний запрос добавлял бы задержку каждому подключению. Вход по-прежнему закреплён за идентичностью машины, поэтому другой Host по чужому маршруту токен не получит.

Осталось (8b), переключение маршрута у живого подключения при обрыве. По разведке кода это возможно без перезагрузки view: HTTP и заголовки WebSocket читают `connection.host` на каждый запрос, а страница читает `streamBaseUrl` лениво при каждой физической попытке сокета. Что нужно: заменить `RemoteDesktopHost` на экземпляр, вошедший по новому маршруту (токен для повторного входа есть только у сохранённой машины); перерегистрировать `onHeadersReceived` под новый адрес mux, пока страница не узнала о смене, иначе 401 старого mux разорвёт подключение; закрытие подключения должно читать `connection.host`, а не захваченный экземпляр; новый IPC с адресом для страницы, который мутирует `__OCEAN_TRANSPORT__.streamBaseUrl` (preload и `apps/web/src/main.ts`); обновить заголовок окна, меню и `hostSelection`; `remoteForget` искать машину по идентичности, а не по адресу. Сделано 2026-11-25 по этому дизайну: `switchRemoteRoute` в `apps/desktop/src/main.ts`, крючки `onConnectionLost` и `onRouteChanged` на транспортном объекте страницы (`packages/client/connection/src/client/index.ts`), мост в `preload-app.ts`, клей в `apps/web/src/main.ts`. Ниже — как к этому пришли. Триггер решён 2026-11-25 — сообщение от страницы: в main нет сигнала о сетевом обрыве, есть только 401, который main обрабатывает сам. Состояние `disconnected` для этого не годится: контроллер публикует его только при offline браузера, а неудачные попытки дают лишь `connecting`, и ноутбук, ушедший из домашней сети, остаётся онлайн. Поэтому плагин считает неудачные retry (`onReconnectRequested`) и вызывает `transport.onConnectionLost` на третьем подряд и затем каждом десятом; при offline попыток нет и отчёта нет. Страница через новый IPC передаёт это в main; main спрашивает остальные маршруты машины тем же `answeringRoute` и при ответе переключает подключение. Периодическая проверка отклонена — она тратит трафик и батарею; пункт меню отклонён — он не переключает автоматически. Возврат на более быстрый маршрут, как в T3 Code, остаётся открытым вопросом и в 8b не входит.

### Шаг 9. Remote-only режим Desktop

Локальный Host можно выключить: Desktop не запускает свой Host и показывает только удалённые машины и форму подключения. Какие функции требуют локальный Host (обновления, локальные настройки, терминалы) и что они делают в этом режиме — после исследования.

Сделано 2026-11-25. Настройка `localHost.startAtLaunch` в `settings.json` (по умолчанию `true`, отсутствие или неверное значение читается как `true`); меняется чекбоксом **Start local Host at launch** в меню приложения и действует со следующего запуска. При старте без Host не вызывается `reconcileBackend`: не грузится локальный документ, не запускается процесс Host, не выполняется `applyRelease` локальных плагинов. Форма подключения становится документом главного окна (`showRemoteHome`): те же обработчики, закрытие формы перезагружает её, успешный вход не закрывает окно. Приложение само входит в последнюю сохранённую машину (выбор маршрута из шага 8a), иначе ждёт ввода. «Use local Host» скрыт, `hostSelection` без локального пункта, `selectHost('')` отклоняется; после отключения последнего Host приложение возвращается к форме. Ограничения: на Windows и Linux меню приложения запрашивает страница приложения, поэтому без подключённого Host доступны только кнопки формы; обновления и аккаунт в этом режиме вручную не проверялись.

Вторая часть не сделана и требует отдельного решения. Инструменты `browser_*` (`packages/browser-use/tool-browser-desktop/src/install.ts`) управляют вкладкой, которой поделился человек, через мост в главный процесс приложения, где эта вкладка нарисована (`requester.request(sessionId, 'screenshot' | ...)`). При удалённом Host агент работает на Host, а вкладка нарисована на клиенте, поэтому нужен обратный канал «Host → действие в приложении клиента»: клиент объявляет сервис, Host его проксирует, и всё это под правом устройства. Это новая архитектурная поверхность (клиентский Remote-сервис, адвертайзинг возможностей клиента, политика доступа к браузеру клиента), а не расширение существующего потока. Нужно решение о безопасности: разрешать ли Host управлять браузером клиента, кому и с каким подтверждением. Без него реализация была бы догадкой, поэтому она отложена, а не сделана наполовину.

10a. Проброс порта. Кадры потока — JSON, поэтому байты идут base64. Сделано 11c (2026-11-27), переключение пресета разрешений. Селектор в чате пишет пресет единственным путём — слеш-командой `/permission`, то есть через `commands/execute`, которого не было ни в одном праве: каталог пресетов устройство читало, а переключение получало отказ. `commands/execute` внесён в `sessions:write`. Устройство получает все слеш-команды сессии (`/model`, `/compact`, `/export`, `/goal`, `/plan`, `/skill`); это не расширяет его возможности, потому что `settings:manage` уже позволяет ему менять пресет по умолчанию для всех новых сессий.

Осталось за решением владельца. Устройство со всеми правами по-прежнему не может:

- устанавливать, обновлять и удалять плагины (`pluginManager/*`, `pluginInventory/list`) — это загрузка кода на Host, нужно отдельное право либо явное включение в `settings:manage`;
- пользоваться сессионными возможностями вне карты — целями (`goals/*`), расписаниями (`schedule/*`), фоновыми задачами (`job/*`), скиллами (`skills/list`), пресетами (`agentPresets/*`), сабагентами (`subagents/*`), командами (`agentTeams/setEnabled`), обратной связью (`messageFeedback/*`, `sessionFeedback/record`); по JSDoc все они привязаны к одной сессии или агенту и могут уйти в `sessions:read` и `sessions:write` одним изменением карты;
- управлять аккаунтом (`account/*`) и устройствами (`devices/*`) — намеренно только владельцу;
- открывать файлы и каталоги в приложении на рабочем столе Host (`session/openWorkspacePath`, `session/canOpenWorkspacePath`, `session/workspacePathApplications`, `settings/openSettingsDocument`) — действие на машине Host бессмысленно для удалённого клиента.

Отдельно от прав: редактирование файлов в клиенте отсутствует у всех; ошибка хода `MISSING_CREDENTIAL` в чате показывается сырой диагностикой Host с общей подсказкой «Choose another model», без действия «открыть Models».
